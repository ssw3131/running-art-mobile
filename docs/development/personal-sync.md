# 개인 코스·러닝 동기화

2026-10-03 구현. 실제 검증 범위는 [검증 보고서](../quality/personal-sync-verification.md)를 따른다.

## 사용 흐름

1. 내 계정에서 Google로 로그인한다. 로그인 자체는 기존 기기 자료를 계정으로 옮기거나 업로드하지 않는다.
2. **개인 기록 동기화 켜기**는 현재 계정의 코스·완료된 러닝을 전송하고 서버 기록을 복원한다. **기기 기록을 이 계정에 연결**은 계정 미연결 코스·완료된 러닝도 현재 계정에 귀속한다. 안내에서 계정 연결·서버 전송을 확인한다.
3. 기기에 먼저 저장하며 앱이 전경에 있을 때 30초 간격으로 동기화한다. 실패하면 30초부터 최대 5분 간격으로 재시도하고 **지금 동기화**로 즉시 다시 시도할 수 있다. 앱이 백그라운드로 가거나 계정이 바뀌면 진행 중 전송을 취소한다. 잠금 중 GPS 기록과 서버 전송은 별개다.
4. 다른 기기에서 같은 계정으로 로그인하고 동기화를 켜면 목록과 경로를 복원한다. 코스 경로와 종료한 러닝의 좌표·요약을 검증한 뒤 한 트랜잭션으로 반영한다.
5. 기기와 서버의 같은 기록이 함께 변경되면 자동 덮어쓰기를 중단한다. 내 계정에서 **이 기기의 변경 유지** 또는 **서버 내용 사용**을 선택한다. 삭제와의 충돌도 안내하며 명시적 선택 전까지 기기 내용을 보존한다.

계정 연결 기록은 로그아웃하면 숨겨지고 같은 계정에서 다시 보인다. 계정 미연결 자료는 로그아웃 상태에서 사용할 수 있다. 로그아웃·자동 동기화 끄기는 자료 삭제가 아니다. 진행 중인 본인/비회원 러닝은 종료한 뒤 로그아웃/로그인한다. 세션 소실 시에는 마지막 저장 지점에서 중단하며 같은 계정으로 다시 로그인해 재개한다. 다른 계정에 남은 중단 기록이 재로그인을 막지 않는다.

테스트 메모·도로 캐시·인증 세션은 개인 기록 동기화 대상이 아니다. 배경 지도 오프라인 표시, 공유·커뮤니티·회원 탈퇴는 이 기능과 별도다.

## 저장 계약

- SQLite 버전 4: 기존 코스·러닝·좌표·메모의 원래 필드를 보존하고 `owner_id`, 서버 버전, 전송 대기, 변경 식별자를 추가한다. 코스의 같은 경로 중복 저장 방지는 계정 범위로 수행한다. 서로 다른 기기에서 각각 생성한 별도 ID는 별도 기록이다.
- `sync_accounts`: 계정별 이 기기의 동기화 활성화와 마지막 전체 완료 시각. `sync_deletions`: 기기 삭제 후에도 남는 재전송 대기. `sync_conflicts`: 명시적 해결 전까지 유지하는 서버 변경 정보.
- 모든 저장소가 같은 SQLite 실행 대기열을 공유해 GPS 저장과 서버 복원의 트랜잭션이 겹치지 않게 한다. 계정 소유권 검사는 목록뿐 아니라 상세·수정·삭제에도 적용한다.
- 서버 `personal_records`: `(owner_id,kind,record_id)` 키, 단조 증가 버전, 변경 ID, 요약, 파일 경로·SHA-256, 삭제 표시. 좌표 원문은 DB 요약과 분리한다.
- 비공개 Storage 버킷 `personal-records`: `계정 UUID/course 또는 run/기록 ID/SHA256.json`. 최대 24 MiB JSON. 파일을 먼저 업로드하고 서버가 존재를 확인한 뒤 요약을 공개한다. 같은 해시 파일의 재업로드는 중복으로 처리한다.
- `commit_personal_record`: 로그인 사용자 ID를 서버에서 얻고 예상 버전·변경 ID를 검사한다. 기기 시계로 승자를 정하지 않는다. 테이블 직접 쓰기는 금지하고 본인 읽기·서버 함수 쓰기만 허용한다.
- 삭제는 서버에 삭제 표시를 남기고 비공개 파일을 Storage API로 제거한 뒤 기기 대기를 해제한다. 파일 제거 실패도 재시도한다. 살아 있는 기록이 참조하는 파일은 삭제 정책으로 보호한다.
- 한 작업에는 같은 계정의 인증 토큰을 고정한다. 나중에 계정이 변경돼도 요청을 새 계정으로 바꾸지 않는다. 원문 오류·토큰·개인 좌표를 진단 로그에 기록하지 않는다.
- 복원 전 계정·기록 ID·종류·버전·파일 경로·해시·좌표·개수·요약을 검사한다. 러닝은 같은 구간 좌표의 거리 재합계도 비교한다. 진행 중인 러닝은 업로드·덮어쓰기 대상에서 제외한다.
- Android의 `Blob.text()`에 의존하지 않고 Supabase `download().asStream()`을 사용한다. 수신 중 24 MiB·30초 한도를 검사하고 UTF-8 바이트를 합친 뒤 해시를 대조한다. 중복 업로드도 기존 서버 파일의 내용을 대조한 뒤 완료로 처리한다.

## 서버 배포와 검증

모바일 전용 `running-art-mobile-dev`에 [마이그레이션](../../supabase/migrations/20261003023000_personal_records.sql)을 2026-10-03 대시보드 SQL Editor에서 한 트랜잭션으로 실제 적용했다. Supabase CLI 마이그레이션 이력에 등록한 작업은 아니다. 신규 테이블·버킷과 정책을 생성하며 재실행은 중복 생성 오류를 낸다. 현재 앱에는 기존 공개 연결 설정만 사용하고 서버 관리 키를 넣지 않는다. 서버 환경 분리 여부는 기존 제품 결정대로 후속이다.

[정책 검사](../../supabase/tests/personal_records.sql)는 임시 사용자·메타데이터를 트랜잭션 안에서 만들고 `ROLLBACK`한다. 실제 Google 사용자나 개인 기록을 수정하지 않는다. 호스팅된 Storage는 SQL 직접 삭제를 금지하므로 파일 제거는 앱의 Storage API 검증으로 확인한다. 이 보호 설정을 끄지 않는다.

공식 계약: [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)·[Storage 접근 정책](https://supabase.com/docs/guides/storage/security/access-control)·[React Native 파일 업로드](https://supabase.com/docs/reference/javascript/storage-from-upload).

주요 코드: `src/modules/sync/`의 모델·SQLite·서버 어댑터·동기화 엔진·앱 수명, `features/auth/SyncPanel.tsx`의 계정 연결·상태·충돌 선택.
