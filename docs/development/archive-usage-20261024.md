# 기록 보관함·코스 상세·사용 횟수 계약

2026-10-24 사용자 수정 계획을 따른다. 통합 폴더는 `running-art-archive`, 브랜치는 `feat/archive-usage`다. 가입 폴더의 `c3285e1` 기반 변경과 20km 작업을 대조해 통합했다. 원래 가입·20km·모바일 작업 폴더는 구현 대상으로 사용하지 않는다. 초기 범위는 소스·격리 검사·APK였으며, 사용자 후속 승인으로 PR/CI·병합·운영 반영·SM-S942N 설치까지 확대했다. [후속 결과](../quality/archive-release-20261025.md)를 따른다.

## 화면과 이동

- 저장 코스는 모든 저장 자료를 표시한다. 코스 ID 또는 동일한 불변 코스 사본의 가장 최근 도전이 미완주이면 태그를 표시한다. 도형 종류만으로 묶지 않는다.
- 완주 기록은 종료 확정된 `completed/finished` 코스 기록만 SQL에서 먼저 걸러 페이지로 조회한다. 자유 러닝·중도 종료·도착 확인 대기는 삭제하지 않으며 기존 통계에 남는다.
- 홈의 두 더보기는 저장 코스로 이동한다. 홈 개별 연결 코스는 코스 상세, 자유 러닝은 러닝 상세, 완주 목록은 완주 기록 상세로 이동한다. 원본 삭제 시 러닝 사본은 읽기만 하며 자동 저장하지 않는다.
- 이전 버튼은 내비게이션 이력을 사용한다. 직접 실행된 상세에 이전 이력이 없을 때만 관련 목록으로 이동한다. 목록 탭·스크롤은 마운트된 상태로 유지한다.
- 후보·저장 코스는 `CourseDetailScreen`을 공유한다. 저장 전에는 명시적 저장이 필요하다. 저장 완료 후 같은 화면에서 러닝·GPX·삭제로 전환한다.
- 최근 미완주에는 ‘이 코스 러닝 이어하기’. 진행/중단 세션은 기존 화면에서 명시적으로 재개한다. 이미 종료된 기록은 안내 후 새 도전이며 과거 거리·시간을 합산하지 않는다. 다른 활성 세션이 있으면 먼저 정리한다.
- 완주 상세는 최초 도형 획득 기록에 배지, 후속 완주에 트로피를 표시한다. 실제 기록의 거리·시간·지도·공유·재도전을 제공한다. 경사 조회 실패 시 난이도를 꾸며내지 않는다.

## 사용량과 복구

정책 초기값은 성공한 생성 5회·누적 신규 저장 15회다. 앱은 `usage` Edge Function에서 버전·사용량·총량을 읽는다. Supabase `usage_policy` 수정은 기존 회원에게 즉시 적용되고 변경 이력은 `usage_policy_history`에 남는다. 총량을 낮춰도 사용량이나 자료는 삭제하지 않는다. UI는 사용/총량으로 표시하고 진행 막대만 100%로 제한한다. 자동 충전·결제·가격표는 없다.

새 계산과 저장은 온라인 가입 완료 회원만 허용한다. 동기화 OFF도 예외가 아니다. 로컬 자료 열람·GPX·기존 코스 러닝은 네트워크를 필요로 하지 않는다. 같은 계정의 가입 완료 영수증은 오프라인 진입에만 사용하며 서버 작업 권한을 대신하지 않는다.

`usage_subjects` 행 잠금 아래 예약과 확정을 직렬화한다. 생성은 v1/v2 요청에 Bearer 인증과 UUID 작업 ID를 붙인다. 서버만 생성 예약·후보 준비를 수행한다. 0후보·실패·확정 전 취소는 미차감이다. 1개 이상 후보를 수령한 클라이언트가 확정하면 묶음당 1회 차감한다. 취소와 확정은 먼저 완료된 상태를 따른다. 확정 결과는 계정 삭제 때까지 원장에 남아 응답 유실을 복구한다. 기기 journal은 결과 화면 표시 후 해제한다. 서비스 경로에는 로컬 계산 fallback이 없고 엔진 자체 검증 경로는 유지한다.

저장은 `usage_pending`에 불변 사본을 먼저 안전하게 준비한 뒤 서버 예약·확정·로컬 공개 순으로 처리한다. 로컬 준비 실패는 미차감이다. 서버 확정 후 연결/프로세스/최종 공개 실패는 실패 확정이 아닌 복구 대기이며, 같은 작업으로 공개를 재시도한다. 원장 중복·이미 보관 중인 사본·이름 변경·기존 동기화 복원에는 추가 차감하지 않는다. 삭제 의도도 로컬에 남겨 다음 온라인 저장 전에 서버를 정리한다. 삭제한 사본의 재저장은 새 사용이다. 러닝 자체 저장은 제한하지 않는다.

신규 저장 ID는 서버 원장의 `usage_saved_courses.course_id`와 SQLite·동기화 파일에서 동일하다. 기존 자료의 동기화/복원은 기존 저장소 경로로 유지하여 도입 이전 자료를 차감하지 않는다. 서버 사용량은 선택적 자료 동기화와 독립적이다.

## 재가입·권한

서버가 Supabase Auth에서 검증한 제공자와 안정된 `sub/provider_id`를 비밀 HMAC 키로 처리한다. 이메일이나 임의 내부 ID로 계정을 합치지 않는다. 연결된 제공자들은 같은 주체로 결합하고 사용량을 합산한다. HMAC 비밀키를 임의 교체하면 기존 사용 주체를 찾을 수 없으므로 운영 키의 보존·접근 통제가 필요하다.

탈퇴 의도 등록 시 주체 잠금 아래 미확정 작업을 취소한다. 기존 탈퇴 절차로 Auth·프로필·코스·GPS·작업 상세가 지워진 후 HMAC와 누적 카운터만 남는다. 무료 혜택 정책 운영 기간까지 보관하며 총량 변경은 기간 종료가 아니다. 정책 종료 시 운영자가 비활성화하고 잔여 작업/연결/카운터/HMAC를 삭제한다. 일반 회원은 원장을 직접 조회·수정할 수 없고 Edge Function의 허용된 명령만 호출한다.

## 운영 적용 절차

1. 현재 운영 migration의 수동 적용 상태와 정책 테이블을 대조한다. 기존 약관/지원 migration을 통째로 재실행하지 않는다.
2. 격리 환경에서 `20261024120000_usage_allowances.sql`을 적용하고 가입 완료 계정·재가입·권한·동시 요청을 검사한다.
3. Edge Function `usage`와 Cloud Run 양쪽에 같은 `USAGE_IDENTITY_HMAC_KEY` 및 서버 전용 Supabase URL/service role 설정을 연결한다. 키는 앱·문서·로그에 넣지 않는다.
4. 계산 API의 인증 필수 버전과 앱을 함께 릴리스한다. 이전 익명 앱은 계산이 차단되므로 업데이트 안내가 필요하다. 기존 공통 과부하 보호는 유지한다.
5. Dashboard의 `usage_policy` singleton에서 `generation_limit`, `save_limit`을 변경한다. 사용량/원장을 직접 초기화하지 않는다. 정책 버전·이력과 기존 회원 조회 반영을 확인한다.
6. 정책 종료는 단순 한도 변경과 구분해 승인·기록한 뒤 `active=false`로 신규 작업을 중지한다. 운영자 SQL 트랜잭션에서 `usage_saved_courses`, `usage_operations`, `usage_owners`, `usage_identities`, `usage_subjects` 순으로 정리한다. 정책 변경 이력은 식별값을 포함하지 않는다. 이 문서는 해당 삭제를 실행하지 않는다.

usage SQL·Edge Function·Cloud Run 및 도메인 전달은 10-24 밤 운영 적용했다. 기존 수동 migration 이력을 보존하며 같은 SQL을 다시 실행하지 않는다. 정책 총량 변경은 위 5번으로 관리한다. 정책 종료/식별값 삭제는 실행하지 않았다.
