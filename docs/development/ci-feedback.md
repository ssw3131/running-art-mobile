# 변경 검토·독립 진단·CI 효과 관측

이 절차는 기획이 바뀌는 개발에서 오래된 테스트 기대를 제품 정답으로 오인하거나, 후반 실패마다 전체 검사를 반복하는 일을 줄인다. [전체 검증 운영](verification-ci.md)과 필수 게이트는 유지한다.

## 1. 같은 PR에서 결정과 검사를 연결

`npm run qa:plan -- main`으로 관련 분야를 확인한다. 코드·자산·검사·의존성·워크플로 등 문서 외 변경은 `docs/quality/change-reviews/<작업명>.json`에 한 작업당 하나의 검토 기록을 추가한다. 기존 기록은 역사로 남기며 새 작업에서 재사용하지 않는다. 함께 수정한 기록만 현재 PR 근거로 인정한다.

```json
{
  "schemaVersion": 1,
  "paths": ["src/features/example.ts", "tests/example.test.mjs"],
  "behavior": "changed",
  "decision": "결정 일시·사용자 지시 또는 최신 기획 경로와 이전 결정을 대체하는 이유",
  "before": "변경 전 사용자가 겪는 동작",
  "after": "변경 후 기대 동작. 기획 유지이면 유지하는 이유",
  "invariants": ["기존 자료·설정·권한·실패 복구에서 그대로 지킬 조건"],
  "tests": [{"path": "tests/example.test.mjs", "reason": "갱신한 검증 내용, 또는 기존 검사로 충분한 이유"}],
  "visual": {"status": "unchanged", "reason": "화면 유지 이유"},
  "native": "필요한 분야별 진단·최종 전체 검사, 또는 불필요한 이유"
}
```

예시 경로는 실제 변경 경로로 교체한다. `behavior`는 `changed`/`preserved`, 화면은 `changed`/`unchanged`/`not-applicable`이다. 화면이 바뀌면 `visual.evidence`에 원본·기준·차이 검토 경로/실행과 검토 근거를 적는다. 필수 승인자를 새로 요구하지 않는다.

`npm run qa:review -- main --working`은 미커밋·새 파일까지 검사한다. CI는 PR의 실제 base~checkout 변경을 검사한다. draft에서는 누락을 안내하고 ready에서는 실패시켜 비싼 Android 실행 전에 고친다. 문서만 변경하면 기록을 강제하지 않는다. 경로·검사 파일·설명의 존재를 검사할 뿐, 문장이 올바른 기획인지 자동 판정하지 않는다. 기존 테스트를 정답으로 간주해 앱을 바꾸지 말고 최신 결정과 대조한다. 화면 마스크·허용 오차와 자료 보존 조건은 이 기록으로 완화하지 않는다.

## 2. 분야별 진단의 시작 상태

수동 Verify의 home/generation/service/achievements/accessibility는 각 시나리오 직전에 전용 에뮬레이터 앱을 초기화하고 실제 격리 회원 세션·공개 자료를 다시 준비한다. 전체 회귀의 연속 내비게이션/재시작 상태 검증은 그대로 유지한다. visual은 기존처럼 새 자료를 준비한 뒤 독립 화면을 촬영한다.

- 각 진단은 동기화 OFF·활성 러닝 없음·원본 코스/메모 존재를 확인한다.
- 생성 진단은 홈의 실제 조건 진입 CTA와 거리 버튼 탐색으로 준비한다.
- S234는 자체적으로 공개 러닝 코스 fixture를 넣는다. 앞선 준비 시나리오를 통과한 것으로 간주하지 않는다.
- 시나리오마다 원본 자료 불변을 확인한 후에만 다음 초기화를 수행한다. 앞선 자료 훼손을 초기화로 숨기지 않는다.
- `report.json`의 `setups`와 `*-setup.json`은 준비 증거다. `steps`의 실제 검사 성공과 구분한다. 준비 실패도 시간·오류를 남긴다.
- 실패한 실제 단계도 시작/종료/소요 시간을 기록한다. 게스트·가입 등 기존 단계의 세부 시간이 없는 과거 보고서는 추정값으로 채우지 않는다.

PC Python 도구 검사는 실제 Android 통과가 아니다. 단독 모드는 `manual-verification`이며 병합용 전체 증거를 발행하지 않는다. 다른 기기의 설정·휴대폰 자료·제품 코드는 변경하지 않는다.

수동 `suite=android`, `android_scenario=diagnostics`는 여섯 분야를 각기 새 러너/에뮬레이터에서 실행한다. 독립성 점검용이며 매번 실행하지 않는다. 각 APK 빌드 비용이 발생하고 호스팅 동시 실행 한도에 따라 대기할 수 있다. 평소에는 관련 분야 하나를 선택한다. ready의 Android36 전체/29 호환 검사와 이름은 유지한다.

## 3. 다음 10/20 PR 측정

[관측 설정과 수동 분류](../quality/ci-observation.json)의 `since` 이후 생성된 main 대상 **문서 외 변경 PR을 생성 순서로 최대20개** 관찰한다. 이번 개선 PR도 첫 표본에 포함한다. 10개 병합 시 중간 검토,20개 병합 시 비교한다. 닫힌 미병합 PR은 실패/취소 비용을 숨기지 않도록 표에 남으며, 이런 PR 때문에20개 병합에 도달하지 못하면 표본 확장 여부를 명시적으로 결정한다.

`Observe verification`은 Verify 완료 이벤트마다 원본 회차별 메타데이터를90일 아티팩트로 보존한다. 기본 브랜치의 코드와 읽기 전용 API만 사용하고 PR 코드·아티팩트를 실행하지 않는다. 제품 필수 게이트와 독립적이며 관측 실패는 관측 미완료로 표시한다. 예약·자동 게시·배포는 없다.

누적 비교는 Actions의 `Observe verification → Run workflow`, 또는 읽기 전용 GitHub 토큰을 환경변수 `GH_TOKEN`에 둔 환경에서 `npm run qa:metrics`로 실행한다. 토큰을 명령 인자나 기록에 넣지 않는다. 결과는 `test-results/ci-metrics/window.json`/`window.md`와 Actions 요약이다. 공개 저장소의 무인증 조회는 API 한도 때문에 실패할 수 있으며 일부 결과를 성공으로 내지 않는다.

수집 항목:

| 항목 | 정의 |
| --- | --- |
| 전체 검사 시간 | PR 전체 성공 실행의 경과시간 중앙값/P95와 표본수. 병렬 작업 시간을 합하지 않음 |
| 첫 실패 피드백 | 해당 실행 시작~최초 실패 step 완료. 큐·사람의 수정/검토 시간과 별개 |
| PR당 반복 | 전체 검사 시작 회차·실패·취소. 같은 run 재실행도 각 회차 포함 |
| main 재사용 | 동일 트리 재사용/전체 실행이 관측된 main 중 재사용 비율. 문서만 변경 제외 |
| 실패 원인 | product/test-contract/environment/unclassified. 최초 실패를 성공 재실행으로 지우지 않음 |
| 병합 후 회귀 | 검토한 PR 수와 근거가 있는 회귀 건수. 미검토를0건으로 해석하지 않음 |

실패 원인은 `failures`에 `{ "runId": 123, "attempt": 1, "category": "test-contract", "evidence": "실패 단계/원본 및 결정 대조 근거" }`로 추가한다. 집계 단위는 실행 회차이며 여러 원인이 섞여 주원인이 불확실하면 미분류를 유지한다. 단순 UI 타임아웃을 환경 장애로 단정하지 않는다.

병합 후 확인은 `postMergeReviews`에 `{ "pr": 55, "evidence": "확인한 날짜·범위·근거", "regressions": ["관련 이슈/PR와 재현 근거"] }`를 적는다. `regressions: []`도 확인 범위가 있어야 하며 앱 전체 무결함을 의미하지 않는다.

기존 기준은 draft2분57초/전체37분32초/main 재사용30초의 **개별 사례**다. 새 중앙값과 인과적인 전후 개선율로 비교하지 않는다. 실행 횟수 감소와 원인별 실패 감소, 병합 후 회귀를 함께 보고 다음 정책을 결정한다. 장기 표본이 쌓이기 전에는 효과 검증 완료로 기록하지 않는다.
