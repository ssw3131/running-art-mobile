# 코스 계산 성능 개선과 웹 비교

2026-09-27 기준. 결과와 탐색 범위를 바꾸지 않는 첫 최적화를 구현했다. PC 결과를 휴대폰 속도로 해석하지 않으며 기기 측정 상태는 [현재 상태](../handoff/status.md)와 [검증 기록](../quality/route-engine-verification.md)에 남긴다.

## 전략과 구현

서울 OSM·광화문·하트·5km·반경 2km를 공통 입력으로 잡았다. 원본과 같은 최대 200/140/80개 평가, 순서·동점 처리·Math.hypot 거리·점수 수식·거리 및 중복 제한을 유지한다. 같은 전체 결과가 나오면 불필요한 재계산과 할당부터 줄인다.

Node CPU 프로파일에서 A* 함수 자체가 약 11.79초, 거리 함수 4.96초, 최근접 노드 함수 3.70초의 샘플 시간을 차지했다(3회 합계, 인라인 함수의 비용은 호출자에 포함될 수 있음). 점수 계산을 바꾸거나 탐색 수를 줄이는 대신 아래를 적용했다.

- 최근접 노드: 축별 거리가 현재 최단 거리보다 크면 제외하고, 남은 노드는 원래 Math.hypot와 엄격한 `<` 동점 규칙으로 비교한다. 연결 가능한 노드·회전 노드를 숫자 열/행 인덱스로 검색마다 한 번 준비해 문자열 키 생성과 반복 필터링을 줄인다. 셀·노드 순서는 그대로다.
- A*: 검색 하나에 Float64 비용/휴리스틱, Int32 이전 노드, 세대 스탬프를 두고 재사용한다. 힙 순서와 같은 비용 후보의 처리 순서는 보존한다. 이미 더 싼 경로가 있으면 휴리스틱 계산을 생략한다.
- 경로 캐시: 같은 검색 안에서 `(출발 노드, 도착 노드, 정확한 길이 예산)`을 키로 성공·실패를 재사용한다. 방향과 예산을 생략하지 않는다. 최대 8,192개 경로·262,144개 노드 ID로 제한하고 원형 FIFO로 제거한다. 검색 종료·취소 후 다른 작업에 공유하지 않는다.
- 힙: 이동할 항목을 보관하고 부모/자식만 빈 자리로 이동한 뒤 마지막 자리에 넣는다. 반복 속성 접근과 교환 쓰기를 줄이되 왼쪽 우선의 엄격한 비교와 동점 순서는 보존한다. 8ms 실행 예산과 A* 32회 방문 체크포인트는 유지한다.

캐시는 결과를 저장한 기준 파일과 무관하다. 모든 배치를 실제 평가하며 진단 수치는 결과 객체 바깥 `metrics.routing`에 기록한다. 동시 generator와 취소 후 재실행은 별도 검색 상태를 사용한다. 실행 중 입력 그래프를 외부에서 수정하는 것은 지원하지 않는다.

## 같은 PC에서 재현

```powershell
. .\scripts\env.ps1
node scripts/benchmark-route-engine.mjs --engine tests/reference/v02/src/route-engine.js --runs 3 --output .cache/route-performance/original-node.json
node scripts/benchmark-route-engine.mjs --runs 3 --output .cache/route-performance/current-node.json
```

다른 저장 사례는 `--case seoul-heart-v02`처럼 지정한다. 각 회차에서 그래프를 다시 만들고 그래프/탐색/총시간을 기록한 뒤 **전체 결과**를 보존 기준과 정확히 비교한다. `--engine`으로 별도 보존한 수정 전 엔진도 지정할 수 있다. CPU 프로파일은 `node --cpu-prof --cpu-prof-dir=.cache/route-performance scripts/benchmark-route-engine.mjs --runs 3`로 수집한다. 프로파일 켠 시간과 끈 시간을 섞어서 개선율을 계산하지 않는다.

아래는 Node v24.21.0, 프로파일 없이 각 3회, 같은 PC·같은 입력의 순차 실행이다. UI·호스트 실행 양보가 없는 동기 측정이며 개발 기기/호스트 부하 변동을 통제한 전문 벤치마크는 아니다.

## 배포 웹앱과의 비교

사용자 제공 [웹앱](https://running-art-seoul-mobile.alo-ha.chatgpt.site/)은 기본 v0.3이다. [보존 v0.2 화면](https://running-art-seoul-mobile.alo-ha.chatgpt.site/v0.2/)으로 이동해 광화문·하트·5km·반경 2km를 맞췄다. 배포된 v0.2 엔진의 LF 정규화 SHA-256은 모바일 참조와 같은 `43a5a0f6bff98b6697d98ee10be85865a9328225b87345e613f8707864ab2fbf`다.

웹 API는 11,266개 요소, 앱 표본은 ID 정렬한 4,810개 요소를 전달한다. 그래프 생성 후에는 모두 21,627노드·23,132도로이며 삽입 순서는 다르다. 웹 API 입력을 보존 원본으로 실행한 전체 결과와 앱 고정 기준을 오차 0으로 비교해 일치했다. 웹 UI에서도 6,280개 배치, 386개 경로 평가, 107개 유효 후보와 같은 추천 5개를 확인했다. **웹 브라우저 자동화의 완료 대기는 연결 문제로 실패했으므로 브라우저의 정확한 실행 시간은 아직 미확정**이다. 위 Node 원본 8.50초를 웹 브라우저 측정이라고 부르지 않는다.

웹 원본의 `route-worker.js`는 Web Worker에서 동기 엔진을 실행한다. 모바일은 Hermes의 JS 스레드에서 화면·입력 처리와 계산을 공유하고, generator를 통해 실행을 양보한다. 수정 전 폰의 전체 59.95초 중 연산 구간 합계는 51.76초, 구간 밖은 8.20초였다. 따라서 대기 제거만으로 웹과 같은 속도가 된다고 단정할 수 없다. 런타임·개발 모드·하드웨어의 기여는 분리 측정이 필요하다. [React Native 공식 성능 문서](https://reactnative.dev/docs/performance)도 개발 모드 성능과 릴리스 측정을 구분하도록 안내한다.

## 기기 측정과 실행 모드

최종 엔진을 개발용 JavaScript로 실행한 휴대폰 3회는 53.266 / 61.152 / 58.435초, 중앙값 **58.435초**였다. 수정 전 단일 관측 59.955초와 차이가 작고 반복 편차가 크므로 실기기 개발 모드의 뚜렷한 개선으로 보지 않는다. 에뮬레이터는 301.050초 → 199.753초로 약 33.6% 줄었다. 모두 서울 하트 5km이며 원본 전체 결과가 허용 오차 1e-6 이내로 일치했다. 폰 계산 중 입력·취소·재시작과 메모리 관측도 완료했다. 기기별 수치·제한은 [검증 기록](../quality/route-engine-verification.md)에 있다.

추가로 같은 개발 APK에 `dev=false`, `minify=true` JavaScript를 공급했다. 휴대폰은 **39.417 / 44.265 / 48.873초**, 중앙값 **44.265초**로 개발 모드 중앙값보다 약 **24.2%** 줄었다. 에뮬레이터는 **82.148 / 106.403초**였다. 모든 결과가 원본 전체 비교 `match`이며 두 기기에서 입력·취소·재시작도 확인했다. 실행 모드도 큰 영향을 주지만 엔진 변경 전후 개선율과 모드 변경 효과를 합쳐 하나의 알고리즘 개선율로 보고하지 않는다. 열·백그라운드 부하 등을 통제하지 않았고 반복 편차가 있으므로 특정 기기에서 항상 이 속도가 난다고 보장하지 않는다.

개발용 진단 코드의 영향을 따로 확인할 때 기존 Metro를 종료하고 `npm run start:performance`를 사용한다. Expo의 `--no-dev --minify` 옵션으로 **같은 development APK에 배포용 JavaScript**를 공급한다. 개발용 경고·Fast Refresh 조건이 일반 `npm run start`와 다르며 네이티브 릴리스 APK 성능 검증은 아니다. 코드 개발은 `npm run start`로 돌아간다. 두 서버를 같은 프로젝트에서 동시에 실행하지 않는다.

## 후속 판단

2026-09-27 후속으로 [독립 실행 테스트 APK](android-test-apk.md)를 빌드·설치했다. 휴대폰의 Metro 연결 없이 같은 입력 3회가 **24.832 / 23.752 / 27.961초**, 중앙값 **24.832초**였고 모두 원본 전체와 일치했다. 입력·취소·재시작도 통과했다. 기존 테스트 서명을 사용하는 release variant이며 앞선 개발 APK + 배포용 JavaScript와 구분한다. 세부 수치·환경·APK 해시는 [검증 기록](../quality/route-engine-verification.md)에 있다.

1. 충분한 휴지 시간과 열·부하 조건을 기록해 장시간 반복과 다른 기기도 확인한다. 이번 단일 휴대폰 측정만으로 출시 성능이나 웹 대비 배수를 확정하지 않는다.
2. 웹 브라우저의 정확한 시간도 같은 입력에서 다시 측정한다. Node 원본 시간으로 대신하지 않는다.
3. 남은 계산 비용이 크면 Hermes 프로파일을 근거로 별도 실행 스레드·네이티브 계산을 검토한다. 현재 구현을 별도 스레드라고 설명하지 않는다. 별도 스레드는 화면 응답성에 도움이 될 수 있지만 연산 자체가 빨라진다는 보장은 없다.

이번 결과 보존 최적화와 개발 기기 검증을 완료했다. 알고리즘 29개와 기존 기능 29개, 합계 58개 테스트·타입·린트·Android 번들이 통과했다. 6개 고정 전체 결과와 A* 방향/동점/예산 경계, 최근접 경계, 상태 재사용·취소 경계를 포함한다. 휴대폰에서도 여전히 수십 초가 걸리므로 제품 성능이 완료됐다는 의미는 아니다. 최적화 검증 종료 당시 두 기기는 Metro 8081의 성능 비교 모드였으며, 이후 폰은 독립 실행 릴리스 APK로 업데이트했다.
