**작업 브랜치에서 개발하고, PR에서 핵심 앱 동작까지 자동 검증한 뒤 main에 합친다.**

## 2. 브랜치 전략

계속 유지하는 브랜치는 **main 하나**, 개발할 때 **작업별 임시 브랜치**를 만든다. GitHub Flow를 기준으로 한다. [공식 안내](https://docs.github.com/en/get-started/using-github/github-flow)

| 브랜치 | 용도 | 예시 |
|---|---|---|
| `main` | 검증을 통과한 기준 코드 | 기능 완료본 |
| `feat/*` | 기능 구현과 관련 테스트 | `feat/s1-onboarding` |
| `fix/*` | 결함 수정과 회귀 검사 | `fix/oauth-cancel` |
| `chore/*` | CI·검증 도구 구성 | `chore/verification-ci` |

**작업 흐름**

`main에서 분기 → 구현·로컬 검사 → 커밋·push → PR → CI·화면 확인 → squash merge → 작업 브랜치 삭제`

- UI와 API를 상시 브랜치로 분리하지 않는다. 가입 화면·동의 API처럼 함께 동작하는 변경은 기능 단위로 묶는다.
- 큰 단계는 독립적으로 검증 가능한 작은 PR로 나눈다.
- 필수 검사 실패나 미해결 화면 차이가 있으면 합치지 않는다.
- main에 합치는 것과 폰 설치·서버 배포는 별개다.
- 현재 S0 미커밋 변경을 보존해 작업 브랜치로 옮긴다. S0 정리 후 CI 구축은 별도 브랜치에서 진행한다.
- GitHub의 브랜치 보호 기능 사용 가능 여부를 확인하고, 가능하면 필수 검사와 직접 push 제한을 적용한다.

## 4. CI 트리거와 결과 처리

| 발생한 행동 | CI 동작 |
|---|---|
| 로컬 파일 저장·커밋 | GitHub CI는 실행하지 않음. 로컬 검사 수행 |
| 작업 브랜치 push, PR 없음 | 자동 실행하지 않음 |
| main 대상 PR 생성·재개 | 빠른 검사 + 관련 핵심 앱 흐름 |
| 열린 PR의 브랜치에 추가 push | 최신 코드로 재검사 |
| main에 변경 반영 | 구현된 전체 회귀 검사 |
| `Run workflow` 수동 실행 | 선택한 검사 묶음 실행 |

GitHub 이벤트는 `pull_request`, main 대상 `push`, `workflow_dispatch`를 사용한다. [공식 트리거](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)

- **PR:** API 36에서 핵심 앱 흐름과 변경 관련 화면을 검사한다.
- **main:** 전체 회귀·API 36 화면 비교·API 29 호환 핵심 검사를 실행한다.
- **문서만 변경:** 링크·문서 구조만 검사한다.
- 공통 내비게이션·인증·저장·의존성 변경은 검사 범위를 넓힌다. 분류되지 않는 제품 변경은 전체 검사 대상으로 둔다.
- 오래된 중복 실행 취소·캐시·아티팩트 보관 기간으로 사용량을 관리한다. 무료 제공량과 지출 차단 설정을 확인하고 시작한다.
- 첫 실패 뒤 진단용 재실행이 성공해도 불안정한 검사였다는 기록을 유지한다.

자동 보고서에는 **시나리오·소스/APK/시험 자료 해시·기기 환경·실패 단계·기준/현재/차이 이미지·로그**를 연결한다. 개인 계정·실제 GPS 원본은 CI에 올리지 않는다.
