## 결론

같은 v0.2 엔진의 강남 계산은 SM-A750N 78.52초, 이 PC의 Node 동기 실행 중앙값 4.75초였다. 서버 방식의 실익을 확인할 근거가 있으며 실제 호스팅 시험을 권한다. **클라우드에서 4.75초를 보장하거나 Supabase 무료/유료 차이를 측정한 결과가 아니다.**

한 계산 프로세스에서는 요청 4개의 마지막 응답까지 약 20.34초, 두 프로세스에서는 약 10.40초였다. 프로세스 2개는 단일 요청 시간을 줄이지 않았고 처리량을 늘렸다. 저사양 폰 대기 시간과 서버 동시 처리 비용을 함께 판단해야 한다.

## 조건과 정합성

- Windows 10.0.26300, Node v24.21.0 x64, Ryzen 7 5800H, 논리 CPU 16개, RAM 약 15.86GiB. 시작 시 사용 가능 RAM 약 1.74GiB. 일반 개발 PC이며 CPU 할당량/전원·열·백그라운드 작업을 격리하지 않았다. 프로세스 1개를 클라우드 1 vCPU와 동일시하지 않는다.
- [SM-A750N 측정](a750-performance-20261005.md)의 공개 합성 격자·강남 중심·부산 시청을 재사용했다. 합성 격자는 anchored/반경 3km, 실제 도로는 free-loop/반경 2km, 모두 heart/v0.2다.
- 실제 도로 릴리스 `kr-20260930-c8cb96030306-roads-v1`; 휴대폰과 같은 강남 매니페스트 `484c83…9322c`·9파일, 부산 `35ca7c…275df`·6파일을 R2에서 직접 읽고 압축/해제 해시를 확인했다. 전체 해시·옵션·입력 해시는 JSON과 phone-reference에 보존했다.
- Node 기존 모바일 협력형 러너와 동기 실행의 **전체 결과가 3표본 모두 일치**했다. 격자는 휴대폰이 통과한 원본 전체 기준과 일치한다.
- 휴대폰과 그래프 규모·6개 탐색 계수·5후보 점수 순서가 일치한다. 실제 도로 점수의 최대 절대 오차는 `2.842170943040401e-14`다. **실제 도로 후보 전체 좌표는 휴대폰에서 추출하지 않았으므로 휴대폰과 전체 좌표 해시 일치를 검증했다고 표시하지 않는다.**
- HTTP 측정 57응답 모두 전체 결과 해시 일치. 후보 결과를 캐시하지 않고 요청마다 입력 검증·그래프·탐색을 새로 수행했다. 도로 입력만 각 프로세스에서 재사용한다.

폰은 캐시 파일 해제/조립을 매번 수행하고 PC 반복은 입력을 메모리에 유지하므로 전체 시간은 같은 캐시 단계 비교가 아니다. **계산 시간끼리도 하드웨어·Hermes/V8·협력형 스케줄링 차이를 모두 포함**한다. 서버용 다른 알고리즘으로 바꾸거나 탐색을 줄이지 않았다.

| 표본 | 새 프로세스 시작 | 첫 로컬 파일 검증/조립 | 첫 계산 | 시작+첫 HTTP 전체 |
| --- | ---: | ---: | ---: | ---: |
| 격자 | 0.418초 | 0.002초 | 1.202초 | 1.810초 |

| 부산 | 0.148초 | 0.094초 | 1.735초 | 1.984초 |

새 프로세스는 OS 파일 캐시/디스크 cold 상태나 Cloud Run cold start가 아니다. 첫 요청이 반복보다 빠른 표본도 있고 1회뿐이므로 최초 지연 분포를 추정하지 않는다. 공개 R2 다운로드·검증·저장 준비는 별도 1회로 강남 2.524초, 부산 1.639초였고 이 PC의 네트워크 조건이다. 도로 자료가 이미지에 포함된 호스팅 시험 묶음은 요청 시 R2 다운로드를 하지 않는다.

강남 반복의 그래프 구성 중앙값 53.93ms, 탐색 4,688.89ms, 결과 직렬화 1.19ms, 응답 원문 211,442바이트다. 자식 프로세스 CPU 시간 중앙값 5,484ms는 런타임 보조 스레드도 포함해 벽시계 계산 4,748ms보다 클 수 있다. 휴대폰의 `computeMs`는 실제 CPU 계측이 아니므로 이 값과 직접 대조하지 않는다.
