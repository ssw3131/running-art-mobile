# 강남 실제 도로 Hermes 분석과 추가 최적화 실험

2026-10-02, SM-S942N·Android 16·release/Hermes. [직전 실기기 비교](phone-performance-20261002.md)의 후속이다. [측정 JSON](hermes-gangnam-20261002.json)에 입력 식별자·각 실행·CPU/온도 표본·프로파일 집계를 보존한다.

**분석을 완료했으나 추가 속도 개선은 확보하지 못했다.** 병목은 A* 최단 경로와 최근접 노드 탐색이다. 두 구현 실험은 실기기 개선이 일관되지 않거나 오히려 느려 채택하지 않았고, 엔진·실행기는 작업 전 코드로 유지한다. 반복 지연에는 CPU 동작 상태가 영향을 주는 증거가 있지만 제조사 발열/전력 제어를 원인으로 확정하지 않는다.

## 같은 입력과 비교 방법

- PC에서도 같은 전국 공개 캐시를 오프라인으로 읽어 입력을 확보했다. 요소 배열 SHA-256은 `9258ec47bf29173776f888e94524cc156a79c233f68ff080095f452e4efcfd8b`, 전체 결과 SHA-256은 `ef05b665709cf9df5a53d83d8efa76e45f27f6c6ac6640ec830d7bcacb547c05`다.
- 버전 비교는 새 앱 프로세스에서 전1→후1→후2→전2(두 번째 실험은 →전3→후3)를 실행했다. 같은 USB 연결 상태로 CPU 주파수·JS 스레드 CPU 시간·전후 온도를 수집했다. 기기를 재부팅하거나 전력/발열 정책을 고정하지 않았다. 작은 표본과 서로 다른 열 상태 때문에 쌍별 수치도 순수 코드 효과의 확정값은 아니다.

- 최초 3회는 화면 기본값 **3km**가 유지됐다. 같은 3km끼리의 예비 관측으로만 보존하며 5km의 전후·재시작 비교에 섞지 않는다. 이후 도구에 목표 거리·매니페스트·탐색량·후보 점수 일치 검사를 추가했다. USB 단절로 끝까지 수집하지 못한 실행은 정규 비교에서 제외했다.

## Hermes 병목

기존 release APK를 그대로 사용하고 같은 서명의 임시 계측 APK에서 `HermesSamplingProfiler`를 호출했다. 일치하는 release 소스맵과 엔진 소스를 대조했다. 개발 모드·Metro·디버그 앱으로 바꾼 측정이 아니다.

전체 5,743표본 중 엔진 호출이 스택에 포함된 1,830표본을 집계했다. 아래 값은 샘플 비율이며 정확한 함수별 경과 시간이 아니다.

| 구간 | 표본 | 엔진 표본 중 비율 | 해석 |
| --- | ---: | ---: | --- |
| `shortestPathSteps` 본체 | 466 | 25.5% | A* 방문·비용 갱신 |
| `nearestNode` 본체 | 329 | 18.0% | 최근접 노드 탐색 |

자식 호출을 포함하면 A*가 57.5%, 배치 오차 평가(`placementError`)가 20.9%다. 포함 비율과 본체 비율은 겹치므로 합산하지 않는다. GC가 이번 프로파일의 주된 비용은 아니지만, 장시간 누수 부재나 모든 느린 실행의 GC 비중을 증명하지는 않는다.

두 실험 모두 PC에서 같은 강남 입력의 전체 경로·순위·반올림 전 점수와 탐색량이 기존 결과와 정확히 일치했다. 모든 정상 수집된 폰 5km 실행은 기존의 후보 점수 5개와 탐색 진단이 일치했다. 폰 로그는 전체 좌표를 내보내지 않으므로 폰 전체 좌표 비교까지 했다고 해석하지 않는다.

공통 탐색 진단: 요청 147,074·캐시 적중 33,738·실제 탐색 112,509·방문 8,028,589·최대 캐시 경로 8,192·최대 캐시 노드 156,435. 후보 상한·점수/거리 수식·`Math.hypot`·동점 순서·길이 예산·8ms 양보 예산·32방문 체크포인트는 줄이지 않았다.

## 반복 지연에서 확인한 것과 한계

5km 계산의 대부분은 실행 슬라이스 안에서 발생했다. `computeMs`는 슬라이스의 벽시계 시간으로, 실제 CPU 시간과 다르며 GC·선점도 포함한다. 단순히 UI 양보 횟수나 네트워크가 늘어난 현상으로 설명할 수 없다.

계산 중 JS 스레드의 `/proc/.../stat` CPU 시간 증분은 실행 중(`R`) 첫/마지막 표본 사이 벽시계 시간의 약 98%였다(`getconf CLK_TCK=100` 확인). 스레드는 코어 6/8/9 등으로 이동했고 주파수도 달라졌다. 마지막 연속 비교의 첫 실행에서 코어 9 정책의 순간 주파수는 3.456GHz→2.688GHz→1.824GHz였고, 두 번째 실행은 주로 1.632GHz였다. `/proc`와 주파수 파일은 순차로 읽은 순간값이므로 정확한 평균 클럭이나 항상 해당 코어에서 실행됐다는 의미는 아니다.

기존 APK도 새 프로세스에서 21.351초와 27.976초처럼 큰 편차를 보였다. 동일한 요청·탐색량과 새 프로세스에서도 편차가 남으므로, 반복할수록 누적된 JS 객체만으로 지연을 설명하기 어렵다. 동일 프로세스의 3km 예비 관측도 14.534→17.659→17.582초로 느려졌으나 5km와 직접 비교하지 않는다.

마지막에는 기존 APK·5km로 별도 연속 비교를 했다. 같은 프로세스에서 **24.309→28.137초**, 앱을 강제 종료 후 새 프로세스로 실행해도 **27.856초**였다. 계산 후 배터리 온도는 각각 36.5/36.7/37.1°C다. 재시작한 실행도 코어 9 정책의 순간값은 대부분 1.632GHz였다. 이 관측에서는 프로세스 재시작만으로 속도가 회복되지 않았다. 충분히 식힌 뒤의 회복량·충전 해제 조건은 검증하지 않았다.

관측 동안 배터리/표면 온도가 올라가고 CPU 주파수가 변했다. Android 열 상태 값은 계속 0이었다. 제조사 DVFS·발열/전력 관리·스케줄링·다른 앱 부하를 각각 통제하지 않았으므로 **발열 제한의 정확한 원인·비중은 미확정**이다. 한 기기의 충전 연결 조건에서 얻은 결과이며 장시간 메모리 누수·야외 배터리 검증과도 구분한다.

`scripts/qa/build-hermes-profile.ps1`은 현재 개발 서명으로 임시 계측 APK를 만든다. 대상 앱 ID는 `com.runningart.mobile.dev`이며 대상 APK와 같은 서명이 필요하다. 사용자 DB 스냅샷은 별도 `snapshot` 모드에서 읽기 전용으로 수행한다. 개인 위치를 포함하므로 `.cache` 안에서만 보관한다.

```powershell
. .\scripts\env.ps1
powershell -ExecutionPolicy Bypass -File scripts/qa/build-hermes-profile.ps1
adb -s <기기> install -r .cache/hermes-gangnam/probe/probe.apk
adb -s <기기> shell am instrument -w -e mode profile com.runningart.hermesprobe/.ProfileInstrumentation
```

계측 명령이 `Hermes sampling enabled`를 출력한 뒤 폰에서 코스 계산 검증 화면의 서울 실제 도로→강남→오프라인→하트 5km를 계산한다. 앱을 강제 종료하지 않는다. 계산이 끝나면 다른 터미널에서 다음을 실행한다. 중지 파일이 없으면 도우미는 약 180초 후 자동 종료한다.

```powershell
adb -s <기기> shell touch /sdcard/Android/data/com.runningart.mobile.dev/files/hermes-probe/stop
adb -s <기기> pull /sdcard/Android/data/com.runningart.mobile.dev/files/hermes-probe/profile.json .cache/hermes-gangnam/baseline-profile.json
node scripts/qa/analyze-hermes-profile.cjs .cache/hermes-gangnam/baseline-profile.json .cache/hermes-gangnam/baseline.bundle.map .cache/hermes-gangnam/profile-analysis.json
adb -s <기기> uninstall com.runningart.hermesprobe
```

소스맵은 **측정한 APK를 빌드했을 때의** `android/app/build/generated/sourcemaps/react/release/index.android.bundle.map`을 보존해 사용한다. 이후 재빌드한 다른 소스맵을 섞지 않는다. 로컬 원자료는 `.cache/hermes-gangnam/`에 있고 공개 문서에는 개인 기록·원시 DB·UI 덤프를 넣지 않았다.

다음 성능 작업은 가장 큰 A*·최근접 탐색의 비용을 줄이는 구조 변경을 별도 검토한다. 별도 실행 스레드만 도입하면 UI 응답성에는 도움이 될 수 있지만 CPU 계산량 감소를 보장하지 않는다. 네이티브 구현을 검토할 때도 전체 경로·점수·동점 순서·탐색량 대조가 선행돼야 한다.
