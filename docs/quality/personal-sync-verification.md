# 개인 코스·러닝 동기화 검증

**2026-10-05 새 형식 휴대폰 후속 완료:** v2/v3 코스·연결 러닝의 오프라인 수정/재시작/4건 재전송, 빈 SQLite의 8기록(4코스·4러닝·455좌표) 복원을 내용 해시까지 확인했다. 시험 자료 정리 후 기존 2코스·2러닝·209좌표·1메모와 계정/동기화 ON을 보존했다. 두 물리 기기 동시 시험은 미실시다. [최신 검증](phone-validation-20261005.md).

2026-10-03 (Asia/Seoul). **구현·서버 적용·SM-S942N 검증 완료.** [실행 계획](../history/executed-plans/2026-10-03-1112-personal-sync.md)·[계약과 사용법](../development/personal-sync.md).

## 현재 확인한 결과

- SQLite v3→v4의 원래 필드·코스·메모·GPS 보존, 계정 미연결→명시적 연결, 계정별 CRUD, 두 별도 SQLite 간 복원, 전송 실패/응답 유실/재시도/동시 수정/삭제, 충돌 선택, 계정 변경, 손상 거부, 페이지·여러 배치 검사를 통과했다.
- 최종 전체 검사 **220/220**, 타입·린트·Android release 빌드를 통과했다. 실제 SQLite 검사 15개와 설치된 Supabase SDK 검사 2개, 진행 중 러닝의 계정 변경 보호 검사를 포함한다.
- 개발용 Supabase의 새 테이블·서버 함수·비공개 Storage를 실제 적용했다. 본인/다른 계정/비로그인의 읽기·쓰기·파일 업로드 경계, 테이블 직접 쓰기 차단, 중복 재전송·오래된 버전의 충돌·삭제 표시·좌표 파일 불변 검사를 실제 Postgres에서 통과했다. 임시 Auth 사용자 0명 잔존을 확인했다.
- Storage의 SQL 삭제는 공급자의 보호 기능으로 거부됨을 확인했다. 보호를 유지하고 SQL 검사는 해당 거부를 기대하도록 수정했다. 실제 파일 삭제는 아래 Android 앱의 Storage API로 통과했다.
- SM-S942N의 업데이트 전후와 최초 서버 동기화 후, 기존 코스 1개·메모 1개·러닝 2건/209좌표의 원래 필드 해시가 모두 일치한다. PC로 원문 DB·GPS를 추출하지 않았다.
- 휴대폰의 기존 로그인 세션을 유지한 채 기기 코스 1개·완료 러닝 2건을 계정에 연결했다. 전송 대기 0건·동기화 완료를 확인했다. 서버 집계는 코스 1·러닝 2·GPS 209·비공개 파일 3개, 버킷 공개 여부 false다.

## 실제 휴대폰 후속 검증

- **로그아웃·재로그인:** 로그아웃하면 코스·러닝 목록이 각각 비어 있고, 동일 Google 계정 재로그인 후 코스 1개·러닝 2건이 다시 표시된다. 원본 삭제 없이 계정 범위만 바뀐다.
- **오프라인·수정 재전송:** 별도 합성 코스 1개를 전송한 뒤 앱 UI에서 Wi-Fi·모바일 데이터가 꺼진 상태로 이름을 수정했다. 실패 안내·대기 1건과 강제 종료/재시작 후 대기 보존을 확인했다. 통신 설정은 `finally`에서 원래 값으로 복원했다. 재연결 후 대기 0건, 서버 버전 1→2·이름 변경을 확인했다.
- **실제 파일 삭제:** 같은 합성 코스를 앱 UI에서 삭제하고 동기화했다. 서버 버전 3·삭제 표시 true·요약 NULL, 비공개 파일 4→3을 확인했다. 검증용 삭제 표시 1개는 재등장 방지 계약대로 남으며 합성 좌표 파일은 제거됐다. 원래 코스·러닝은 변경하지 않았다.
- **빈 저장소 복원:** 원본 DB/WAL/SHM을 휴대폰 내부에 복사하고 fsync·SHA-256을 대조한 뒤 새 SQLite를 만들었다. 기존 계정으로 동기화를 켜 **12:25:21 KST에 복원 3건**을 확인했다. 코스 1개·완료 러닝 2건·GPS 209좌표의 원래 필드 해시가 원본과 모두 일치했다. 메모는 동기화 대상이 아니므로 새 저장소에 0개인 것이 정상이다.
- **원본 복귀·정리:** 해시 검증 사본에서 원본 DB를 복귀했고 메모 1개까지 모두 일치했다. 임시 사본 폴더·검증 도우미 `com.runningart.authdigest`·기기 UI 덤프를 제거했다. 앱 ID·서명·최초 설치일·계정 세션을 유지했다. 최종 상태는 기존 계정 로그인·동기화 켜짐이다.
- 처음 복원 시 Android Blob에 `text()`가 없어 다운로드에 실패했다. Supabase SDK의 응답 스트림을 직접 읽고 24 MiB·30초 한도를 확인하도록 수정했다. UTF-8 분할 수신·중복 업로드의 원문 대조·초과 스트림 취소 검사를 추가하고 위 실기기 복원을 다시 통과했다.

빈 저장소 복원은 **동일 실제 휴대폰에서 별도 SQLite로 수행**했다. 서로 다른 물리적 휴대폰 2대의 동시 실행은 하지 않았다. 두 저장소의 충돌·수정·삭제 전파는 자동 검사, 다른 계정/비로그인 서버 접근 차단은 실제 Postgres 정책 검사로 검증했다. 장시간 잠금·야외 GPS 정확도·배터리·대규모 데이터·iOS·회원 탈퇴는 별도 후속이다.
