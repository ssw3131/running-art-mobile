# Supabase DB 개선 방향

**2026-10-13 실제 적용 후속:** 운영 구조·기존 서비스 함수 13개·권한·수동 이력을 대조하고 S1 회원/동의 SQL을 적용했다. 3계정 대기 이관과 기존 자료 보존·접근 차단을 확인했다. 약관 게시와 CLI 마이그레이션 이력표 등록은 아직 후속이다. [적용 근거](../quality/s1-phone-db-20261013.md). 아래 검토 당시 미조회·미적용 설명과 구분한다.

2026-10-13 검토안. 현재의 개인 코스·러닝 저장과 동기화 구조는 유지하고, 가입·동의·상품·통계에 필요한 저장 구조를 해당 기능 단계에서 추가한다. 전면 재작성보다 기존 자료와 앱 버전의 호환성을 보존하는 확장을 우선한다.

이 문서는 개선 방향만 기록한다. DB 변경·서버 배포·CD 구축을 시작하거나 완료한 계획이 아니다. 현재 구조의 판단 근거는 저장소 SQL과 기존 배포 기록이며, 운영 DB와 코드의 현재 일치 여부 및 대용량 성능은 별도 확인 대상이다.

## 유지할 기반

- `personal_records`의 소유자·기록 종류·기록 ID를 기준으로 개인 자료를 구분하고, DB와 비공개 Storage의 접근 권한을 함께 유지한다.
- 서버 버전과 변경 식별자로 충돌·재전송을 처리하며, 삭제 표시를 보존해 오래된 기기에서 삭제한 기록을 되살리지 않도록 한다.
- 목록과 요약은 DB에, 긴 코스·GPS 원문은 비공개 JSON 파일에 저장한다. 공개 공유는 별도 사본으로 관리하고 원본의 접근 범위를 확대하지 않는다.

기존 계약은 [개인 자료 동기화](../development/personal-sync.md), [프로필과 사진](../development/account-expansion.md), [공유 링크](../development/run-link-sharing.md), [탈퇴 처리](../development/account-mypage.md)를 따른다.

## 다음 DB 배포 전 구조와 이력 대조

기존 개인 기록 SQL은 Supabase SQL Editor에서 직접 적용했고 CLI 마이그레이션 이력에 등록한 작업은 아니었다. 운영 DB의 테이블·제약·함수·권한·Storage 정책을 저장소의 마이그레이션 및 배포 기록과 대조한 뒤, 이미 적용한 변경과 새로 적용할 변경을 확정한다. 기존 생성 SQL을 그대로 재실행하거나 운영 DB를 초기화해 이력을 맞추지 않는다.

변경 이력 정리는 실제 스키마 대조를 근거로 수행한다. 이후 변경은 새 마이그레이션으로 관리하고, 빈 시험 DB의 생성뿐 아니라 기존 구조에서의 업그레이드와 자료 보존도 검증한다. 이전 앱이 사용하는 필드·함수는 호환 기간을 고려해 유지한다. [Supabase 마이그레이션 안내](https://supabase.com/docs/guides/deployment/database-migrations)

## S1 회원 상태와 동의 이력

닉네임·사진 표시용 계정 메타데이터와 가입 완료·동의 이력의 책임을 분리한다. 회원 상태와 동의는 서버가 관리하는 테이블·함수로 설계하고, 사용자 수정 가능한 계정 메타데이터를 서비스 권한의 근거로 사용하지 않는다. [Supabase 접근 권한 지침](https://supabase.com/docs/guides/database/postgres/row-level-security)

아래는 최초 S1 검토 항목이다. **10-13 가입 우선 구현에서 `memberships`·`membership_consents`·`membership_policies`와 RPC/기존 계정 대기 이관을 구체화했다.** [구현 계약](../development/signup-consent.md)·[검증](../quality/signup-consent-20261013.md). 운영 구조/이력 대조와 실제 DB 적용·최종 약관 게시는 후속이며, 이 문서만으로 운영 DB가 변경된 것은 아니다.

- 계정별 가입 진행·완료 상태와 중단 후 재진입 처리.
- 약관 종류·버전, 필수·선택 구분, 동의 또는 철회 상태와 서버 기록 시각. 보관·삭제 정책은 제품 결정과 함께 확정한다.
- 응답 유실·재전송에서도 같은 동의나 가입 완료 처리가 중복 적용되지 않는 규칙.
- 본인·타인·비로그인 접근, 기존 계정의 진입 경로, 탈퇴 시 처리와 기존 코스·러닝 보존.

가입 보너스의 실제 지급과 상품 권한은 S7 계약에 연결하며, S1에서 가짜 지급 완료나 잔량을 만들지 않는다. 기존 닉네임·사진을 별도 프로필 테이블로 옮길지는 기능상 필요와 이전 비용을 보고 결정한다.

## S7 상품과 이용 권한

구매 내역·서버에서 검증한 거래·이용 권한·생성 사용 이력을 계정 메타데이터와 분리한다. 지급·차감·복원·환불은 서버가 검증하고, 재전송과 동시 요청에도 중복 지급·차감이 발생하지 않도록 설계한다.

상품 카탈로그와 정책 버전을 구분하고 기존 거래가 어떤 규칙으로 처리됐는지 추적할 수 있게 한다. 재구매·하위 팩·차감·환불·오프라인 규칙은 [현재 비즈니스 모델](../product/business-model.md)의 미정 항목을 먼저 확정한다. 이 검토안으로 상품 정책이나 테이블을 확정하지 않는다.

## 통계와 자료 증가에 따른 보완

현재 구조는 개인 자료의 저장·복원 중심이다. S5 등에서 서버 집계가 필요해지면 날짜·거리·활동 시간처럼 실제 조회에 필요한 값을 컬럼이나 집계 구조로 제공할지 검토한다. 사용자별 홈 통계를 로컬 기록으로 계산할 수 있다면 서버 집계를 선행 조건으로 추가하지 않는다. 랭킹은 확정된 출시 기능으로 취급하지 않는다.

집계 범위·기간·시간대·삭제 반영 규칙을 먼저 정하고, 조회 계획과 측정 결과를 보고 인덱스를 추가한다. 대용량 원본 좌표는 유지하되 집계를 위해 매번 모든 파일을 내려받지 않도록 한다. 경쟁·보상과 연결되는 통계는 클라이언트가 올린 요약을 그대로 신뢰할지 별도 검증 기준을 정한다.

자료가 늘어날 때는 계정별 동기화 시간·전송량·파일 용량을 측정한다. 필요하면 증분 조회와 캐시를 보완하고, 업로드 후 커밋 실패나 파일 교체로 남은 미참조 객체의 정리 기준을 확인한다. 현재 참조 중인 파일과 재시도에 필요한 파일은 보호한다. 삭제 표시의 보존 기간은 오래 오프라인이었던 기기의 복원 규칙과 함께 결정한다. 현재 성능 장애나 파일 누적량을 확인했다는 의미는 아니다.
